# Спецификация: Календарь звонков

Учебный проект Хекслета: сервис бронирования звонков. Владелец публикует типы событий и доступное время, гость записывается на свободный слот, владелец видит записи в админской витрине.

Вне спецификации: платежи, email/SMS-уведомления, мультиарендность, авторизация и логин (владелец — один заранее заданный профиль), отмена или перезапись записи самим гостем.

Термины — по `GLOSSARY.md`: Владелец, Тип события, Слот, Запись, Клиент (гость), Главная страница.

## 1. Сценарии пользователя

### 1.1 Владелец публикует доступное время

1. Владелец открывает `/admin` (логина нет; профиль владельца — из конфигурации приложения).
2. Создаёт тип события: название, длительность (15…480 минут) и режим доступности — «расписание» **или** «ручные окна» (взаимоисключающе).
   - Расписание: рабочие часы по дням недели, несколько интервалов в день (напр. пн–пт, 10:00–12:00 и 14:00–16:00), минуты UTC; интервалы через полночь запрещены; пустой список у дня = день свободен.
   - Ручные окна: абсолютные интервалы; создавать можно только в будущем (`start >= now`), хранить прошлое можно (генератор игнорирует); редактирования нет — удалить и создать заново; пересекающиеся окна разрешены, генератор их сливает.
3. Всё вступает в силу сразу: генератор слотов считает их «на лету», отдельной кнопки «опубликовать» нет.

### 1.2 Гость записывается

1. Гость с главной страницы переходит на `/booking`.
2. В колонке 1 выбирает тип события (название + длительность).
3. В колонке 2 видит свободные слоты, сгруппированные по датам (заголовок: день недели + число + полностью месяц, напр. «вт, 13 октября»). Слоты — только будущие на горизонте `now … now + 14д`; занятые и пересекающиеся с любыми записями (общий календарь владельца) не показываются; если свободных нет — «На ближайшие 14 дней свободных слотов нет.»
4. Выбирает слот (время UTC), в колонке 3 заполняет имя, email и необязательную заметку (≤ 500 символов) и нажимает «Записаться».
5. Успех: зелёный блок «Вы записаны!» с номером записи и ссылкой «На главную».
6. Гонка (слот занят к моменту отправки): сервер отвечает 409, на экране — alert «Слот уже занят. Выберите другое время.» с действием «← Вернуться к слотам» (список перезапрашивается, свободные уже обновлены на сервере). Гость остаётся на странице, ничего не теряет.

### 1.3 Владелец управляет записями

1. В секции «Записи» админки владелец видит будущие и прошедшие записи.
2. Может отменить запись — после отмены время автоматически освобождается (слоты считаются от записей).
3. Удалить тип события, на который есть записи, нельзя; смена длительности действует только на будущие слоты; переименование — всегда; «скрыть/приостановить» не предусмотрено.

## 2. Маршруты и экраны

| Маршрут | Экран | Содержимое |
|---|---|---|
| `/` | Главная | Лендинг о сервисе и возможностях; ведёт на `/booking` (ADR 0001). |
| `/booking` | Запись | Одна страница, три колонки: тип события → свободные слоты (группировка по датам, занятые неактивны) → контакты и запись. Победивший вариант прототипа (тикет «Экраны гостевого сценария»). |
| `/admin` | Админка | Одна страница с секциями «Типы событий» (список, создание/редактирование, удаление с сообщением про записи; у каждого типа — редактор режима: таблица расписания ИЛИ список окна) и «Записи» (таблица + отмена). Подстраниц нет, превью генерации нет. |

## 3. API-контракт

`Content-Type: application/json` везде; даты — ISO-8601 UTC с `Z`, секунды (`2026-10-13T10:00:00Z`); пути без версионирования (`/api/...`); пагинации нет. Хранение — SQLite; время в UTC; таймзона показа — одна константа в конфиге.

Ошибки — единый конверт для гостя и админки: `{ "error": { "code": "...", "message": "..." } }`.

### 3.1 Гостевой API

| Метод и путь | Успех | Назначение |
|---|---|---|
| `GET /api/event-types` | `200` `[{ "id": 1, "name": "Воркшоп", "durationMinutes": 45 }]` | Усечённая проекция для гостя (без режима доступности). |
| `GET /api/slots?eventTypeId=1` | `200` `[{ "start": "...Z", "end": "...Z" }]` | Свободные слоты типа на горизонт `now … now + 14д` (задаёт сервер, параметров `from`/`to` нет). `eventTypeId` обязателен — нарезка зависит от длительности. Только реально свободные: занятые и пересекающиеся с записями исключены. |
| `POST /api/bookings` | `201` `{ "id": 42, "eventTypeId": 1, "start": "...Z", "end": "...Z" }` | Создание записи. Тело: `{ "eventTypeId": 1, "start": "...Z", "name": "...", "email": "...", "note": "..." }` (`note` опционально, ≤ 500). `id` — «номер записи». Контакт в ответ не возвращается. |

Порядок проверок при создании записи (клиенту не доверяем — `start` пересчитывается сам):

1. `event_type_not_found` → **404** — нет типа.
2. `slot_out_of_range` → **422** — `start < now` или `start > now + 14д` (конец включительно).
3. `slot_not_scheduled` → **422** — время не попадает в нарезку расписания/окон дня.
4. `invalid_contact` → **422** — name пуст после trim, email не по `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`, note длиннее 500.
5. `slot_taken` → **409** — пересечение общего календаря (проверяется последним). Гонка гарантированно превращается в 409: транзакция «проверил → вставил» + UNIQUE-индекс `booking(start, end)` (страховка от точного дубля; пересечение типов разной длительности ловит только транзакция).

После `201` время (и любые пересечения) сразу исключается из выдачи свободных слотов; живого обновления у открытого гостя нет — фронт refetch-ит по действию «← Вернуться к слотам».

### 3.2 Админский API (`/api/admin`, без auth)

| Метод и путь | Успех | Назначение |
|---|---|---|
| `GET /api/admin/event-types` | `200` список | Типы с `availabilityMode`. |
| `POST /api/admin/event-types` | `201` тип | Создание: name (trim, непустой), durationMinutes (15…480), availabilityMode (`schedule` \| `windows`). |
| `GET /api/admin/event-types/:id` | `200` тип | Один тип. |
| `PATCH /api/admin/event-types/:id` | `200` тип | Переименование / смена длительности (действует только на будущие слоты). |
| `DELETE /api/admin/event-types/:id` | `204` | Удаление; при наличии записей → **409** `event_type_has_bookings`. |
| `PUT /api/admin/event-types/:id/schedule` | `200` | Заменяет **всю** неделю разлом: `[{ "weekday": 0–6, "startMinute": ..., "endMinute": ... }]`; минуты в пределах суток, start < end. |
| `GET/POST /api/admin/event-types/:id/windows` | `200` / `201` | Окна `[{ "start": "...Z", "end": "...Z" }]`; создавать только в будущем; пересечения разрешены. |
| `DELETE /api/admin/windows/:id` | `204` | Удаление окна; существующие записи не трогает (запись привязана к типу, не к окну). |
| `GET /api/admin/bookings` (+ `?from=`) | `200` список | Журнал записей (будущие и прошедшие). |
| `DELETE /api/admin/bookings/:id` | `204` | Отмена владельцем; время освобождается автоматически. |

Коды админских ошибок: 404 — нет сущности; 422 — `invalid_name`, `invalid_duration`, `invalid_schedule`, `invalid_window`; 409 — `event_type_has_bookings`.

## 4. Модель данных (SQLite)

В БД — только типы, окна и записи; сгенерированные слоты не хранятся. Профиль владельца в БД не хранится — один предзаданный профиль (имя, контакт для главной) живёт в конфигурации.

| Таблица | Поля | Ограничения |
|---|---|---|
| `event_type` | `id`, `name`, `duration_minutes`, `availability_mode` | `availability_mode` ∈ {`schedule`, `windows`}; без is_active. |
| `event_type_schedule` | `event_type_id`, `weekday` (0–6), `start_minute`, `end_minute` | Минуты UTC-дня; несколько окон в один день; пустой список у дня = день свободен. |
| `event_type_window` | `event_type_id`, `start`, `end` | Append-only; окна в прошлом хранятся, чистки нет. |
| `booking` | `id`, `event_type_id`, `start`, `end`, `name`, `email`, `note`, `created_at` | `id` = «номер записи»; `end` замораживается при создании; отдельной таблицы `client` нет; валидация контакта — на уровне приложения. |

Связи и гарантии:

- Все FK → `event_type` с `ON DELETE RESTRICT`.
- `UNIQUE(booking.start, end)` — страховка от точного дубля; главная гарантия от гонки — транзакция с overlap-проверкой.
- Слоты считаются «на лету»: расписание/окна типа, нарезанные по `duration_minutes` («хвост» короче длительности отбрасывается, через полночь нельзя), минус записи общего календаря; выдача — `now ≤ start ≤ now + 14д`.

Жизненный цикл типа события: переименование — всегда; смена длительности — только на будущие слоты; удаление — запрещено, пока есть записи; «скрыть/приостановить» — не делается.

## 5. Критерии приёмки

### 5.1 Главная и роутинг

- [ ] `/` — лендинг с текстами о сервисе и возможностях; ссылка на `/booking` есть (тексты заморожены тестами vitest + RTL — ADR 0002).
- [ ] `/booking` и `/admin` открываются напрямую по URL (client-side router, прямые переходы не 404).

### 5.2 Генерация слотов

- [ ] Горизонт: в выдаче только слоты с `start` в `now … now + 14д` (конец включительно); прошлое не показывается.
- [ ] Нарезка: окно/интервал расписания режется по `duration_minutes` от начала, хвост < длительности отбрасывается; интервалы через полночь отклоняет валидация.
- [ ] Пустые дни (нет расписания/окон) не показываются; день с расписанием без окон = свободен.
- [ ] Окна в прошлом в выдачу не попадают.

### 5.3 Запись гостя

- [ ] Успех: `POST /api/bookings` → 201 с `id`; экран «Вы записаны!» с номером записи.
- [ ] Слот исчезает из `GET /api/slots` сразу после 201 (и на следующий refetch гостя).
- [ ] Запись любого типа блокирует время всех типов (общий календарь): слот другого типа, пересекающийся с записью, в выдачу не попадает.
- [ ] 409 `slot_taken` при гонке: серверный ответ → alert с текстом «Слот уже занят» и возвратом к слотам; форма гостя не теряет введённые данные.
- [ ] Порядок ошибок: несуществующий тип → 404; вне горизонта → 422 `slot_out_of_range`; не в нарезке → 422 `slot_not_scheduled`; плохой контакт → 422 `invalid_contact`; в конфликте → 409 (последним).
- [ ] Пустое состояние колонки слотов: «На ближайшие 14 дней свободных слотов нет.»

### 5.4 Админка

- [ ] CRUD типов: создание с режимом; смена длительности меняет нарезку только будущих слотов (у существующих записей `end` не меняется).
- [ ] `DELETE` типа с записями → 409 `event_type_has_bookings`, UI показывает сообщение.
- [ ] `PUT schedule` заменяет неделю целиком; редактор расписания и список окна соответствуют режиму типа.
- [ ] Создание окна в прошлом → 422; удаление окна не удаляет записи.
- [ ] Журнал: будущие и прошедшие записи видны; отмена записи освобождает время — слот снова появляется в `GET /api/slots`.
- [ ] Валидации: name trim непустой, duration 15…480, weekday 0–6, минуты в пределах суток, start < end.

### 5.5 Контракт

- [ ] Все ответы ошибок — конверт `{ "error": { "code", "message" } }`; даты везде ISO-8601 UTC с `Z`.
- [ ] `GET /api/event-types` не отдаёт `availabilityMode` (гостевая проекция).
- [ ] Инфраструктура: `make ci` (lint, format-check, test, build) зелёный; `make up` / `make health` поднимает стек (api `:3000/api/health` → `{"status":"ok"}`, web `:5173`).
